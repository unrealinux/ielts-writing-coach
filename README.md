# IELTS Writing Coach — 雅思作文批改 Skill

一个可分享的 agent skill：给雅思写作 Task 1 / Task 2 作文做**可复核**的批改——四项分项预估分、逐句错误定位、定向改写、可分享的 Markdown 报告。

> **新手先看 [使用说明 `USAGE.md`](USAGE.md)**——三十秒上手、怎么读报告、故障排查、常见问题。
> 本文件讲的是**它是怎么做的**（结构、设计、竞品定位、版本记录）。
> **要发布给别人用，看 [发布清单 `RELEASING.md`](RELEASING.md)。**

## 这个 skill 解决什么问题

通用 AI 批改雅思作文有三个典型毛病：

1. **给分虚高**。考生实际 6 分，AI 给 6.5–7，考场上才发现差距。
2. **建议不可执行**。只会说"词汇可以更丰富""注意语法"，不指出哪一句、哪一类错、怎么改。
3. **四项乱平**。四项分数都给 6.5，看不出真正拖后腿的是哪一项。

这个 skill 用一套硬规则针对性解决：每条扣分必须引用原文；四项独立判定且必须给出差异证据；错误按统一代码聚类后归纳**错误模式**；报告落成文件以便和下次对比。

## 安装（三种位置，任选其一）

skill 的发现规则是：扫描根目录**下一层**的 `<name>/SKILL.md`。

| 用途 | 放置路径 |
|---|---|
| 只给当前项目用 | `<项目根>/.agents/skills/ielts-writing-coach/` |
| 给本机所有项目用（推荐个人使用） | `~/.agents/skills/ielts-writing-coach/` |
| DSH 用户级 | `~/.dsh/skills/ielts-writing-coach/` |

```bash
# 个人级安装
unzip ielts-writing-coach-skill-v1.0.0.zip -d ~/.agents/skills/

# 或者从 git 克隆
git clone <repo-url> ~/.agents/skills/ielts-writing-coach
```

安装后**无需重启**——运行中的 harness 会监视 skill 根目录，新增或修改会在下一个模型步骤自动进入 skill 目录。

装好后建议跑一次自检，确认文件完整：

```bash
python3 ~/.agents/skills/ielts-writing-coach/scripts/selfcheck.py
```

## 使用

装好后有三种触发方式：

1. **直接说需求**（推荐）：`帮我批改这篇雅思大作文` + 粘贴题目和作文。skill 目录里有描述，agent 会自动加载。
2. **斜杠手势**：消息里写 `/ielts-writing-coach`，skill 正文会直接注入当前对话。
3. **显式点名**：`用 ielts-writing-coach 批改这篇`。

### 输入格式建议

把作文单独存成 `.txt`（**不要**把题目混进作文文件，否则段落统计会把题目算成第一段）：

```bash
python3 scripts/analyze_essay.py essay.txt --task 2 --out stats.md
```

`--task` 取值：`1`（Academic Task 1，≥150 词）、`1gt`（General 书信，≥150 词）、`2`（Task 2，≥250 词）。加 `--json` 输出结构化数据；源文件写 `-` 则从 stdin 读。

**依赖**：仅需 Python 3.8+，只用标准库。脚本缺失时 skill 仍可工作，只是少了客观统计这一层。

## 报告长什么样

批改报告写入 `ielts-reports/<日期>-<任务类型>.md`，包含：

- 一句话结论（当前水平 + 最关键瓶颈 + 提分最快的一步）
- 分数卡（四项 + 总分 + 每项一句话依据）
- 逐项诊断（该档门槛 / 本文证据 / 离上一档差什么）
- 错误清单（位置 → 原文 → 代码 → 修改 → 原因）
- **错误模式小结**（把重复错误归纳成系统性问题）
- 句子升级 before → after（含改动说明）
- 段落结构图、词汇升级表
- 下一步 3 个动作
- 目标分段示范（只示范一段，明确说明不要背诵）

## 带 Word 批注的 .docx 输出

Markdown 报告是写给"读"的，Word 批注是写给"改"的。学生想逐句看批注、或打印给老师看时：

```bash
python3 scripts/report_to_docx.py --essay my.txt --report my-report.md --out MyEssay(reviewed).docx
```

产出包含：

| 内容 | 说明 |
|---|---|
| **真实 Word 批注** | 从报告的「错误清单」生成，锚定在原文的具体词句上（不是括号里的纯文本） |
| **页边标签** | 每条批注首行是短英文标签（`Articles · 冠词`、`Collocation · 搭配`），第二行是修改，理由以小字跟在后面。评分页附**标签统计表** |
| **斜体改写** | 从「句子升级」生成，插在受影响的段落后，附改动说明 |
| **评分页** | 四项分项分 + 依据 + 总分，另起一页 |
| 问题清单 / 错误模式小结 / 下一步 | 与报告一致，便于对照 |

**不依赖 python-docx**——直接用标准库 `zipfile` 写 OOXML 包。

三条诚实性约束（脚本内建）：

1. **定位失败就列为未锚定**，绝不挂到别的句子上。错位的批注会让学生改错地方，比不挂更糟。
2. **同一段原文被多行错误引用时合并成一条批注**，而不是产出两条重叠范围（Word 可能把重叠范围"修复"掉，静默丢掉一条反馈）。
3. **生成后自动校验**：批注 id 一致性、嵌套闭合、必备部件、评分页完整性。校验失败返回非 0，而不是产出一个 Word 会提示"修复"的文件。

输出**字节可复现**（固定 zip 时间戳）：同样的输入得到同样的文件，可以 diff、可以重跑。自检会实际构建两次并比对 SHA-256。

## 跨篇进度追踪

单篇报告是写一次就不再被读的。`scripts/track_progress.py` 扫描报告目录，把它们聚合起来：

```bash
python3 scripts/track_progress.py ~/ielts-reports --out ~/ielts-reports/_趋势.md
```

输出四件单篇报告看不到的东西：

| 内容 | 说明 |
|---|---|
| **分项趋势** | 同一任务类型首篇 → 末篇的变化（Task 1 与 Task 2 分开算，TA 与 TR 不可比） |
| **跨档算术** | 四项总和、距下一档差多少、**若只靠某一项填平差距需要提到多少分** |
| **错误代码跨篇累计** | 哪些代码反复出现、累计多少处 |
| **持续性问题** | 出现 ≥2 篇的代码——**跨篇重复才是系统性弱点的证据** |

**两条诚实性约束**（脚本内建，刻意为之）：

1. **同一天的报告不构成趋势。** 顺序未知时脚本拒绝计算"进步/退步"，改为输出各分项的**分布区间**。把互不相关的几篇按文件名排序再相减，会得出一个虚构的数字——脚本不这么做。
2. **只认 `## 分数卡` 小节。** 没有该小节的 Markdown 会被跳过并列在末尾，因为汇总类文档里的对比表格也含四项分数，全文扫描会把它们误当成批改记录、污染趋势数据。

零依赖、纯标准库、不调用模型——同样的输入永远得到同样的数字。

## 验证

三套验证，都能独立复现：

```bash
python3 scripts/selfcheck.py              # 自检 **189** 项：格式、解析、聚合、docx 结构与幂等性
                                          # 内含 CI 承诺一致性（矩阵起点 = 声明的 3.8+、脚本路径存在）
python3 scripts/check_stdlib_only.py      # 断言所有脚本只 import 标准库
textutil -info out.docx                   # macOS 独立 OOXML 实现能否读取（可选）
```

CI（[`.github/workflows/selfcheck.yml`](.github/workflows/selfcheck.yml)）在 Python **3.8–3.13** 六个解释器上跑上面这些——
3.8/3.9 没有 `sys.stdlib_module_names`，所以矩阵同时也是那条标准库守卫两个分支的覆盖来源。
渲染（docx 画不画得出东西）**不在 CI 里**，原因与手动命令见 `RELEASING.md` §2.5。

自检**会校验上面这个数字**——如果加了检查却没更新它，自检会失败。文档里的声明必须被机器验证，
否则它一定会过时（这个数字此前连续写错三次）。中英两份 README 的数字都会被校验。

## 设计要点

- **分数克制**：内建 Band 锚点（"6.0 是最常见的及格线作文"）与 7 条虚高信号自查表。
- **三个独立的诊断轴**：**错误轴**（语法/词汇错误密度）决定 GRA·LR 的下限；**支撑轴**（证据标记、举例、具体细节、模糊限制语）决定 TR 的上限；**相关轴**（题干关键词覆盖、题型要求的写作动作）决定 TR 的上限。三者可以独立失败，也可以叠加。**一篇零语法错误 → 零论证 → 答非所问的作文，三个轴会依次亮灯，而总分可能高达 7.0。**
- **跑题必须比对题干**：这是工具唯一无法从作文本身推出的判断，所以 `--prompt` 是必需参数而非可选项；误传题目会被拦截而不是产出假阳性。
- **Task 1 ≠ Task 2，而且是两套检测工具**：Task 2 用"论证支撑度"（证据/举例/模糊限制语），Task 1 换成**专项检查**（overview 是否存在、纯报数比例、比较类表达、观点/原因泄漏、时态混用、GT 书信称呼与敬语匹配）。在 Task 1 里数字就是任务本身，把 `percentage` 当"证据标记"会得出完全错误的结论。
- **论证深度可判定**：用"追问三次"把 TR 6 与 TR 7 的分界变成可操作的判据。
- **错误代码化**：30+ 个代码（`GRA-ART`、`LR-COLL`、`TR-UNDEV`…），模式统计才能做。
- **版权处理**：`band-descriptors.md` 是对公开评分标准的中文**原创改写摘要**，非逐字引用，正式评分以官方 Public Band Descriptors 为准。

## 分享给别人

```bash
# 在仓库里对着 tag 打包：内容 = git ls-files，同一 commit 两次打包字节完全相同
git archive --format=zip --prefix=ielts-writing-coach/ \
  -o ../../ielts-writing-coach-skill-vX.Y.Z.zip vX.Y.Z
```

用 `git archive` 而不是 `zip -r`，是因为它**可复现**（时间戳取自 commit，不是「打包那一刻」），
所以发布说明里的 sha256 别人能自己核对；同时它天然只含仓库跟踪的文件，
不需要维护 `-x` 排除清单——那种清单漏写一项就是把个人批改报告打进公开包。

对方解压到上表任一位置即可使用。整包自包含，无外部依赖，无网络请求。

## 已知限制

- 分数是**预估**，不是官方成绩。真实评分由受过训练的考官完成。
- `scripts/analyze_essay.py` 的错误探测是**正则启发式**，有误报和漏报，报告中已注明"需人工确认"；它只用于定位，不参与给分。
- 口语不明显、字迹潦草的手写扫描件需要先转成文本（可配合 `markitdown` skill）。
- 只覆盖写作（Task 1 / Task 2），不含口语、听力、阅读。
